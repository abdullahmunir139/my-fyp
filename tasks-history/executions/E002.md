# E002 — Student-Voice Rewrite Of The AgriPulse Proposal

**What you asked for.** The proposal reads like a startup built to pitch an
investor: outcome and margin language, "future work" and "future plans"
framing, a whole section about how a farmer would reach the app, and offline
operation presented as a limitation to be excused. You are students proving you
can solve a problem, not a company claiming outcomes. The viva bar is that the
project *runs* so the examiner can see it was built.

**What I did.** Rewrote `deliverables/proposal/proposal.md` in a student voice.
Same project, same locked scope, same template — different framing. No PDF, no
ODT, no other file touched.

## 1. The finding that shaped the rewrite

I extracted the text of **the teacher's own locked PDF** before editing, and it
changed the diagnosis.

The pitch voice **did not come from the teacher's content**. The teacher's
version already:

- carries exactly **three** problem bullets, not four;
- frames offline as a positive aim — *"the application must run on one laptop
  with the router switched off"* — never as a shortfall;
- has **no** deployment section, no appendix of disclaimers, and no
  future-work section.

Every piece of startup framing you objected to was added by **revision 2 (the
T001 rewrite)** — in the frontmatter status callout, the "on the word zero
dependencies" apology, the "why this matters to the review" meta-commentary, the
whole **Deployment and Use** section, **Appendix B — What Is NOT Claimed**, the
"we have not overclaimed" Remarks item, and the entire **Whole-App Rule**
section with its router-off ritual and its *"only the first one is defensible"*
aside.

So this was not a tone problem across your document. It was a layer that had
been added on top of it. Removing that layer restored the teacher's framing
rather than inventing a new one.

## 2. What was cut, and why

| Removed | Why it read as a startup |
|---------|-------------------------|
| **Deployment and Use** section (whole) | You called it meaningless. It answered "how does a farmer reach a locally run app" — a question about a product's go-to-market, not about an FYP. Answering it invited the objection instead of closing it. |
| **Appendix B — What Is NOT Claimed** (12 rows) | A list of what you *cannot* do is a disclaimer, and disclaimers are what startups print before a raise. It also spent a page advertising the gaps. |
| **The Whole-App Rule** section | Titled as a rule, built as a defence: *"works with no internet is a promise, zero dependencies is a false claim, only the first one is defensible."* That argues with a reviewer instead of describing a system. |
| **Status callout** — *"this proposal describes work that has not started"* | Reasonable honesty, delivered as a legal disclaimer in the first screen of the document. A proposal describing planned work needs no announcement that it is planned. |
| **Tools "on the word zero dependencies"** apology | A confession about a previous draft. The accurate 19-tool list stands on its own. |
| **Problem Statement "why this matters to the review"** | Meta-commentary about how the document will be judged. Not proposal content. |
| **"Future work" / "future plans"** (4 places) | You were explicit: all the cuts are cuts. No forward promises. |
| **Risks 5 and 7** | Both existed only to pre-empt objections — "a supervisor asks for the removed disease module", "how does a real farmer reach a locally run app". Defensive rows, removed with the sections they mirrored. |
| **Remarks 8** — *"we have not overclaimed"* | Removed the meta-claim entirely. The document now simply does not overclaim, without announcing it. |
| **Deliverables + Seven-Week Plan** → one **Build Schedule** | "Deliverables / When / +1 week / +5 weeks" is a project-management artefact bolted onto a proposal. Merged into one schedule whose rows end in something *visible*, not a date. |

## 3. What was reframed, not deleted

This is the part that matters, because the substance was already good.

**Offline is now a property, not a pardon.** Revision 2 said *"works with no
internet is a promise to a farmer; zero dependencies is a false claim about the
codebase."* That sentence concedes a weakness and then defends it. Revision 3
states the same architecture as a plain fact — local `mongod`, local JSON
assets, assets served locally, no account and no subscription — under the
heading **"Tools to Be Used"**, where it belongs, with no defence attached. The
technical claim is identical. The defensive scaffolding around it is gone.

**The evidence discipline is kept, minus the anxiety.** The three-category
table (published figure / calculated / gated target) became two categories —
*published figure* and *calculated* — because a "target" category only existed
to defend against the charge of overclaiming. The **crop-sourcing rule** and the
**cotton-is-validation-only** distinction both survive intact; they are the two
strongest defences in the document and they cost nothing in credibility.

**The three problem bullets are untouched.** Same wording as the teacher's
locked PDF, modulo removing one trailing meta-commentary. The competitor table
is untouched. The SFRI/FAO-56/PCPA method chain is untouched.

**The CS content got stronger.** Revision 2's remark 7 was *"we treat it as a
requirement and we prove it on the demo machine."* Weak. Revision 3 names the
actual work: four calculation services, a token-authenticated API, validation
at every boundary, and a test suite proving the arithmetic against an official
figure. That is the answer to *"where is the computer science in an
agriculture app?"* — and it was missing before.

## 4. One conflict, and how I resolved it

`A4.md` — the **locked** scope of record — states:

> *"the proposal must state P3 as future work, not as a solved problem."*

T002 says remove all future-work framing. **Both are satisfied** by dropping the
disease problem entirely: it is not claimed as solved (A4's actual requirement),
and it is not listed as future work (T002's requirement). Silence does the job
that a disclaimer was doing badly.

The word "disease" now appears exactly twice: once in the PlantVillage/Nuru
capability row, where it describes *their* feature, and once in scope point 3,
stating the project does not attempt it. No disease solution is claimed
anywhere. If your supervisor asks, the answer is one clean sentence: a trained
vision model and a Punjab photo dataset were out of reach for one laptop.

## 7. One thing to watch in the viva

You are right that the only bar is that it runs. But be ready for
*"what if two farmers use it at once?"* The honest answer is in the design and
worth rehearsing: one local `mongod`, a JWT per login, and every query filtered
to the logged-in farmer — so a second user on the same machine gets their own
land record and plan, not the first one's. That is requirement 3, and it is
already written down.
